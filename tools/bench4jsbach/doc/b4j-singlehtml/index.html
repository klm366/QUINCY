bench4JSBACH documentation¶

Contents:

1. Introduction¶

1.1. Main idea¶

With bench4jsbach we started developing a tool for the scientists of the land department in the Max Planck Institute for Meteorology to make the comparison of JSBACH model simulation output data [ReJSBA] with one another and with data products straight forward and user friendly. In the first instance the tool shall serve for the benchmarking of land models, it has to be able to quantify the deviation of a simulation from reference experiments in the most crucial and/or influential parameters out-of-the-box. This will help developing models as well as managing a larger number of them. It is desirable to cover most research areas of the land department and to keep the tool well adapted to the local technical conditions at the Max Planck Institute for Meteorology.

In order to have a living, dynamical tool, the possibility for individual extension is provided to the user from the beginning. This will help the benchmarking process to retain its validity but also help the scientists to handle future questions bringing new values into focus. It may also foster the communication between the groups as individual developments can easily be made usable for the whole department and thus serve as a basis for a fruitful discussion on the most significant diagnostic for the generally applicable benchmarking in the department.

1.2. Concepts¶

A guiding idea for bench4jsbach is the separation of issues that strongly depend on the origin of the climate data from issues directly related to their comparison. It is intended to solve the origin dependend tasks ‘under the hood’ of the tool so that a scientist can focus on the diagnostic and benchmarking methods.

1.2.1. Experiments¶

We use the generic term experiment independent from the data origin holding earth system model simulation output or observational data. Origin dependend processing like locating and extracting necessary raw data from different host, filesystem and out of datafile but also data interpolation are gathered under the name.

You may assign the role of a reference or that of a candidate to an experiment, in a comparison at least one instance of each is needed. It is possible to have multiple experiments and also a single instance can take both roles in one bench4jsbach run. The main difference of the roles is the comparison being made and the report being written from the perspective of the candidate experiments. Depending on the evaluation method each candidate can be compared with single references or with all references at once.

1.2.2. Diagnostic fields¶

The term diagnostic field clusters processing for the comparison of experiments with a defined set of variables featuring a particular scientific question. It should contain at least one diagnostic and one benchmarking method. In this context the term benchmarking refers to a method that condenses the deviation of two experiments to one number, i.e. yields a global and time average value for it.

2. User guide for benchmarking¶

This chapter shall enable you to use bench4jsbach for the comparison of experiments with predefined diagnostic fields.

2.1. Prerequisites¶

bench4jsbach is developed for UNIX and LINUX operating systems. It is written in object-oriented Python and works with version 2.7. The packages NumPy and NetCDF4 and the 2D plotting library matplotlib are used which are contained in most scientific Python distributions like Anaconda, Miniconda or Canopy. Furthermore bench4jsbach makes use of the benchmarking tool pyCMBS and the climate data command line operators CDO, both inhouse-developments of the Max-Planck-Institute for Meteorology.

We use Anaconda and can highly recommand it, as it simplifies package management and deployment, see http://conda.pydata.org/docs/_downloads/conda-cheatsheet.pdf. From here on it is refered to in the installation process.

Make sure that your system uses Python from opt/anaconda/bin with opt being your Anaconda base directory. If necessary, download and install Anaconda, you can get it from http://docs.continuum.io/anaconda/install#linux-install, and put opt/anaconda/bin to your system PATH. Then update and install the necessary Python packages, ..

>>> conda update conda
>>> conda update anaconda
>>> conda install netcdf4
>>> conda install -c https://conda.binstar.org/scitools cartopy
>>> conda install geos basemap
>>> conda install gdal

.. CDO ..

>>> pip install cdo

.. pyCMBS ..

>>> cd opt
>>> git clone https://github.com/pygeo/pycmbs
>>> cd pycmbs
>>> env OMP_NUM_THREADS=1 python setup.py install

.. and python-redmine ..

>>> cd opt
>>> git clone git://github.com/maxtepkeev/python-redmine.git
>>> cd python-redmine/
>>> python setup.py install

2.2. Get bench4jsbach¶

Change to the root directory of your local JSBACH repository git@git.mpimet.mpg.de:jsbach.git, that is the one containing the .git directory. If you do not have the repository get it with

>>> git clone git@git.mpimet.mpg.de:jsbach.git

Therefore you need passwordless ssh and the access permission for the git server (contact reiner.schnur@mpimet.mpg.de). Switch to the git branch jsbach-dkl

>>> git checkout jsbach-dkl

You will also need passwordless ssh for the servers from which you want to read experiment data.

Being in the git branch jsbach-dkl you find the files for the tool under git/jsbach/tools/bench4jsbach with git/jsbach as your git root directory. The structure of the bench4jsbach base directory bench4jsbach you find initially is shown below.

2.3. Prepare a run¶

A bench4jsbach run consists of two parts, the initial startup run which is done once to set up the environment and create the directory structure and the main run, fetching expriment data, analysing, making plots and writing a report. Both parts are controled by the run script bench4jsbach/scripts/bench4jsbach.py.

2.4. Initial run¶

A bench4jsbach run needs a name as it writes data to your local filesystem that has to be addressed. First choose this run name (e.g. myb4jrun) and change to the base directory bench4jsbach. Call the run script bench4jsbach.py with your run name as command line argument.

>>> cd git/jsbach/tools/bench4jsbach
>>> ./scripts/bench4jsbach.py myb4jrun

While running, the tool writes a welcome and a final success/error message to your display. In addition the internal debugger prints to standard output in the default setting.

2.5. Main configuration file¶

The generated file is a form for the main configuration of your bench4jsbach run and has to be adapted to the planned experiment comparison. It is formatted to be read by a Python config file parser after your accomplishment. A config file consists of key value pairs and sections nested to any depth. For the sections square brackets are used, indentation clearifies the nesting level. You can write comments inline prepended by the hash symbol “#”.

key-1=value-1
key-2=value-2
[section-1]
   key-1=value-1
   [[subsection-1]]
      key-1=value-1

Listing: Basic configuration file supported by a Python parser

3. User guide for developing diagnostic fields¶

In the following we show how a diagnostic for experiment comparison from external sources can be prepared to serve as diagnostic field that may be triggered by a bench4jsbach run. A diagnostic field consists of scripts for the processing chain (preprocessing, analysing, plotting), declarations also for data retrieval and interpolation, descriptive textblocks for generating reports and a configuration file to concentrate the setup. The scripts may be written in any programming language that is supported by your platform. A script has to be layed out for one candidate and one reference so that it is scalable, i.e. it can be called in loops over multiple experiments. It will work on local data which the tool has selected and interpolated from the experiment output beforehand as it had been indicated by the user and the experiment type. The interface of each script has to be declared in a respective section of the diagnostic field s’ configuration file. The information to provide include input and output filenames and possibly hints on format, grid, spatial resolution, tiling and global fragmentation and time resolution and period.

We use the example myb4jrun from the last section User guide for benchmarking again. In the run we want to include some diagnostic and benchmarking for a clear cut out example scientific issue called myfield.

3.1. Declaration in main configuration¶

The central entry point for a diagnostic field into the run is its Diagnostic field section in the main configuration file, in this example myb4jrun.cfg. We declare a subsection called myfield and fill in the path to a new field configuration file as value for the key config_filename, here mypath/myfield.cfg.

### diagnostic fields

[fields]
    [[myfield]]
        config_filename=mypath/myfield.cfg

Listing: Declaration of myfield in main configuration file myb4jrun.cfg

3.2. Configuration file myfield.cfg¶

In this chapter we explain in detail how to develop the field configuration file. The file has to contain all the settings and communication parameters that are needed for a diagnostic field, from fetching experiment output data until writing the benchmark results in a final report.

3.2.1. Top level configuration¶

Top level in the diagnostic field configuration file:

key value
name description datatype default
field_name field id conform to id/name of diagnostic field in main configuration string -
suffix output format suffix for processed data of the run string -
frequency output frequence to use in the run option (yearly, monthly, 6-hourly) monthly
documentation self documentation string None

For verification it will be checked if the value for the key field_name is consistent with the name given for the field in the main configuration.

In our example we fill in the respective values.

field_name=myfield
suffix=nc
frequence=monthly
documentation="""
NAME
        myfield_diagnostic

DESCRIPTION
        This configuration ...

DETAILS
        For all experiments ...
        """

Listing: Example myfield.cfg, top level configuration

3.2.2. Processing chain¶

The processes involved in a diagnostic field are interconnected by I/O dependencies. For the time being they have a binding order: 1. fetch, 2. interpolate, 3. preprocess, 4. diagnose, 5. plot. bench4jsbach works internally with an indexing system in which files are addressed by unique infixes, f.e. VARNAME-INFIX. For each file that shall be written by a process, the appropriate section has to hold a subsection [[VARNAME-INFIX]] which contains the detailed configuration. The infix will also be used as substring for the corresponding filename. If the file shall be read by a subsequent process, it has to be appended to the respective input list. For illustration the listing I/O dependencies at the bottom of the page shows a detail from the configuration file for the diagnostic field myfield. In HTML the graphic serves also as a link to another picture, showing how the I/O dependencies are taken into account.

3.2.3. Fetch section¶

The beginning of the section is marked by the header [fetch]. For each variable that the diagnostic field requires from the experiment output the bench4jsbach run will write a file containing the selected data field. You have to define a subsection f.e. [[VARNAME-INFIX]] for it.

A single subsection in section fetch contains the following key:value entries:

key value
name description datatype default
longname complete name string None
unit physical unit string -

Inside there has to be one subsubsection for each experiment_type given for any item in the experiment section of the main configuration. This subsubsection must be labeled with the respective type name.

Subsubsection for the experiment\ type MPIESM1:

key value
name description datatype default
name name of variable to select string -
code code number of variable to select string -
submodel submodel identifier in the original context string -
stream stream identifier in the original context string -

For clarification we show one variable subsection labeled D_selcode of the fetch section from our example mypath/myfield.cfg.

[fetch]
    [[D_selcode]]
        longname=Surface Downwelling Solar Radiation [W m-2]
        unit=Wm**(-2)
        [[[MPIESM1]]]
            name=swdown_acc
            code=21
            submodel=jsbach
            stream=jsbach

Listing: Example fetch section configuration

3.2.4. Processing sections¶

In order to do the preprocessing, diagnostic and plotting bench4jsbach calls the executable script given for the key exec in the respective section. In the standard case the tool would look in bench4jsbach/prod/scripts for it but you may just as well provide another path. We choose again mypath as path for the executable scripts in the example below, without limiting the generality.

3.2.5. Preprocessing and diagnostic sections¶

Top level in the preprocessing and the diagnostic sections:

key value
name description datatype default
exec executable script to call in bench4jsbach run string -
input input files needed by script stringlist -

In the example below the script myfield_prep.py shall do the preprocessing. It has to read a data file that ought to be found during the bench4jsbach run by the identifier D_selcode as it is given in the value list of the key input. It shall store intermediate results in an output file that can be indexed by D_seasmean . This is indicated by the appropriatly labeled subsection.

[preprocessing]
    exec=mypath/myfield_prep.py
    input=D_selcode,
    [[D_seasmean]]

Listing: Example preprocessing section configuration

3.2.6. Plotting section¶

For the plotting we allow several scripts, the section was adjusted to this requirement.

Top level of the plotting section:

key value
name description datatype default
suffix output format string string -

There are subsections for one or more plotting scripts labeled with a unique identifier for the particular script.

Single plotting script subsection:

key value
name description datatype default
exec executable script to call in bench4jsbach run string -
input input files needed by script stringlist -
nref as indicated by plot: comparison with single or all reference experiment option (single, multiple) -
plot_title title string for plot stringlist -

As in the other processing sections output files are introduced by labeled subsections beneath. In the example below the subsection wds_plot indicates plotting with the script myfield_wds_plot.py. According to the value single for the key nref the script will run seperatly for each candidate, reference experiment pair. It shall read a file indexed by myfield_wds which has to be written by a predecessor process. For each pair it is supposed to store a plot output file with the format png and a title generated from the output infix myfield_wds_plot. For the plots the plot_title has to be used, here consisting of a template and parameters, which should be expanded by the script.

[plotting]
    suffix=png
    [[wds_plot]]
        exec=myfield_wds_plot.py
        input=myfield_wds,
        nref=single
        plot_title='$\Delta_{C_{\%d}R_{\%d}}$',can_no,ref_no,
        [[[myfield_wds_plot]]]

The report section is arranged at the end of the configuration file to improve readabiliy.

Top level in the report section:

key value

key value

technical_TeXed technical description of diagnostic method string -

benchvar name of displayed variable in plotfile string -
benchunit physical unit of displayed variable string -
type type of plot option (map, metric, barchart) -

3.3. Processing scripts¶

The processing scripts ( for preprocessing, diagnostic and plotting ) are run as Python subprocesses. A string list is passed as argument. Each element has the format

"XXX:YYYY"

with “XXX” being a key out of the main or the diagnostic field configuration and “YYY” the corresponding value. The information that should be provided include

  • attributes of the candidate experiment
  • attributes of the reference experiment
  • paths to input files
  • paths to output files

The processes have to parse this string list at runtime to get the keyword arguments.
