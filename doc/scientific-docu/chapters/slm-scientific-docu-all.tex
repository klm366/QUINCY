~\\

\section{Model Init}\label{sec:model_init}

\textbf{Basic structure and functionality:}
\begin{itemize}
\item 1.0 model init: ALLOCATE(jsbach\%models(no{\_}of{\_}models)) and set model options with new{\_}model()
\item 2.0 process config: pass model\%namelist{\_}filename to config and run PROC{\_}config\%init routines (includes reading namelist)
\item 3.0 set model options (e.g., dtime, ics, ice, nc)
\item 4.0 tile init, includes set pft{\_}id and set lct ID (using 2: vegetated)
\item 5.0 grid init: get lon lat from namelist
\item 6.0 process constants init (init{\_}PROC{\_}constants) 
\begin{itemize}
	\item IF (base{\_}config\%set{\_}parameter{\_}values{\_}from{\_}file)  CALL parameters{\_}from{\_}file\%set{\_}param
\end{itemize}
\item 7.0 process memory (t{\_}PROC{\_}memory) init and allocation (\texttt{tile\%mem(PROCESS)\%p})
\item 8.0 lctlib init and read from file data/lctlib{\_}slm{\_}nlct8.def
\item 9.0 time init (e.g., \texttt{dtime = base\_config\%dt}; additional to 3.0 model options)
\item 10.0 IF (base{\_}config\%fluxnet{\_}output) THEN init fluxnet specific simulation output (half-hourly write-out of values for the last full forcing period)
\item 11.0 enable forcing (for all but test{\_}canopy) and run SLM model specific PROC{\_}init routines
\end{itemize}

\section{Process memory}\label{sec:memory_structure_usage}

\subsection{Memory structure}\label{subsec:proc_memory_structure}

Each process has its own memory named \texttt{mo{\_}PROCESS{\_}memory{\_}class} containing two important parts: 
\begin{itemize}
\item a) the memory itself \texttt{t{\_}PROCESS{\_}memory} which is a \texttt{TYPE} that extends \texttt{t{\_}jsb{\_}memory}, and 
\item b) the Subroutine that initializes the memory \texttt{Init{\_}PROCESS{\_}memory} using the \texttt{slm{\_}add{\_}var} Function to allocate and init each single variable of the memory.
\end{itemize}
To create a new variable it needs to be inserted into the process memory and a \texttt{slm{\_}add{\_}var} Function with the variable needs to be created in the init routine. The init value in \texttt{slm{\_}add{\_}var} should always be 0.0{\_}wp (or .FALSE. for logicals); if a different value is necessary use the \texttt{PROC{\_}init} routine to init the variables with this value. \\

A variable as used in the process memories is NOT a standard Fortran variable type such as REAL or INTEGER. Instead it is a TYPE covering much more information than only the value, such as, variable name, the process ID and a variable type identifier (see base/mo{\_}jsb{\_}var{\_}class for the definitions of the variables). Thus, the types of variables in the \texttt{t{\_}PROCESS{\_}memory} can be one of these:
\begin{itemize}
	\item \texttt{t{\_}jsb{\_}var{\_}logical2d}
	\item \texttt{t{\_}jsb{\_}var{\_}real2d}
	\item \texttt{t{\_}jsb{\_}var{\_}real3d}
\end{itemize}
From this list you can see that LOGICAL and REAL variables are supported but not CHARACTER or INTEGER. \\

\textbf{2D and 3D}

Variables in SLM (according to JSBACH4) have a dimension covering the position in the virtual-grid used for globald simulations. Thus, the variable itself manages the values it has across the grid cells. The 2D variables have a x and y dimension at this grid var(x,y), where x is a vector of multiple small areas at this grid (chunk) and y is the block within which the chunks are located: var(ics:ice,iblk) meaning number of the chunk at start and end of the vector and the number of the block. The 3D variables have a x and z and y dimension at this grid var(x,z,y) covering also a vertical dimension z, i.e., soil layer and canopy layer: var(ics:ice,layer,iblk). The name of each 3D variable is always appended by either a \texttt{{\_}sl} or a \texttt{{\_}cl}.

The scientific routines in SLM, however, may generally operate at a certain point in the grid, e.g. var(4,2) the 4th chunk in block number 2, by either looping over ics:ice or using Fortran vectorization with ELEMENTAL routines.

SLM (and JSBACH4) operates at one block only. So the y in var(x,y) and var(x,z,y) is a fixed number (predefined by the atmosphere model to which SLM is coupled such as ECHAM or ICON). Accordingly, the dimensionality of variables as used throughout the scientific routines is reduced by one dimension, that is, 2D -> 1D (var(x,y) -> var(x)) and 3D -> 2D (var(x,z,y) -> var(x,z)).

\subsection{Memory usage}\label{subsec:proc_memory_usage}

Note: the SLM memory structure is under constant development. The information you find is is valid for SLM trunk at revision r628 (2017 June 21nd), but might be outdated at the time you read this (please ask Jan for questions).

The usage of the variables in memory is consistent across all processes, but the usage of pools/fluxes is currently NOT consistent across process (i.e., veg and sb).\\

Preface to the below information: The SLM processes (veg, assimi, ...) are structured by two different types of routines: a) \texttt{update{\_}} and b) \texttt{calc{\_}}. The \texttt{update{\_}} routines are named Tasks and are \texttt{CALL}ed in the Task Queue (see \ref{subsec:task_queue}) in the mo{\_}land{\_}model{\_}interface. The \texttt{calc{\_}} routines are \texttt{CALL}ed only from a \texttt{update{\_}} routine but never from the Task Queue. For example: \texttt{update{\_}phenology()} and \texttt{calc{\_}phenology()}.

Generally the \texttt{update{\_}} routines make the variables available via a pointer to the variables in the process memory, while the \texttt{calc{\_}} routines get the variables they need passed as argument.\\


\textbf{\textsc{Variables}}

In the \texttt{update{\_}} routines the necessary steps to make available a variable are:
\begin{enumerate}
	\item USE the process memory of the variable adding the statement: \\dsl4jsb{\_}Use{\_}memory(PROC{\_}) \\-> replace PROC with the large caps process abbreviation (i.e., A2L, L2A, SEB, TURB, SOIL, HYDRO, VEG, HD, RAD, ASSIMI, PHENO, SB); \\add this statement above the line that says "IMPLICIT NONE"
	\item add to section 0.3 "Declare Memory : Declare process configuration and memory Pointers" the statement: \\dsl4jsb{\_}Def{\_}memory(PROC{\_})
	\item add to section 0.3 "Declare Memory : Declare pointers to variables in memory" the statement: \\dsl4jsb{\_}Real2D{\_}onChunk :: variable{\_}name \\-> use dsl4jsb{\_}Real3D{\_}onChunk for 3D variables and dsl4jsb{\_}Logical2D{\_}onChunk for 2D logicals
	\item add to section 0.5 "Get Memory : Get process memories" the statement: \\dsl4jsb{\_}Get{\_}memory(PROC{\_})
	\item add to section 0.5 "Get Memory : Get process variables" the statement: \\dsl4jsb{\_}Get{\_}var2D{\_}onChunk(PROC{\_}, variable{\_}name) \\-> use dsl4jsb{\_}Get{\_}var3D{\_}onChunk(PROC{\_}, variable{\_}name) for 3D variables; \\these statements differ only between 2/3D but cover both REAL and LOGICAL
	\item within the \texttt{update{\_}} routine you can use the variable as: var(:) or var{\_}cl(:,:), e.g., n{\_}fixation(:) and fn{\_}chl{\_}cl(:,:)
\end{enumerate}
~\\


\textbf{\textsc{Pools/Fluxes}}

Pools (and fluxes) are obviously different from variables in both the way they are created in memory and the way they are used in the scientific code. Moreover, the usage of pools is very different between the veg and the sb process.

In the veg and sb memory, pools are defined as a TYPE that contains another TYPE or variables. For example: veg\%pool\%leaf\%carbon - veg is usually the vegetation process memory, pool is a TYPE that contains other TYPEs, leaf is a TYPE that contains variables (here: carbon).\\

For making pools available in the scientific code currently no such "statements" as available for variables (e.g., dsl4jsb{\_}Get{\_}var3D{\_}onChunk(PROC{\_}, variable{\_}name)) exist for pools or their variables. Pools from veg and sb memory should be made available in the \texttt{update{\_}} routines only, not in the \texttt{calc{\_}}, consistent with the usage of variables. Making pools available in an \texttt{update{\_}} routine includes the following steps:
\begin{enumerate}
	\item USE the process memory of the variable adding the statement: \\dsl4jsb{\_}Use{\_}memory(PROC{\_}) \\-> replace PROC with the large caps process abbreviation (i.e., A2L, L2A, SEB, TURB, SOIL, HYDRO, VEG, HD, RAD, ASSIMI, PHENO, SB); \\add this statement above the line that says "IMPLICIT NONE"
	\item add to section 0.3 "Declare Memory : Declare process configuration and memory Pointers" the statement: \\dsl4jsb{\_}Def{\_}memory(PROC{\_})
	\item add to section 0.3 "Declare Memory" right above the part "Get local variables from options argument" one of the two lines:
\begin{itemize}
	\item TYPE(t{\_}veg{\_}memory), POINTER :: veg
	\item TYPE(t{\_}sb{\_}memory),  POINTER :: sb
\end{itemize}
	\item add below section 0.5 "Get Memory" the according one of the two lines: 
\begin{itemize}
	\item veg  => veg{\_}{\_}mem
	\item sb   => sb{\_}{\_}mem
\end{itemize}
	\item within the \texttt{update{\_}} routine you can access the pools and variables by:
\begin{itemize}
	\item veg\%pool\%leaf\%carbon\%ptr
	\item sb\%pool\%microbial\%carbon\%ptr(ics:ice,:,iblk) (see \ref{subsec:proc_memory_structure} "2D and 3D" for details)
	\item[->] see below for reasons of this differences between veg and sb
\end{itemize}
\end{enumerate}
~\\

\textbf{Dimensionality:} variables in veg pools are SCALAR (t{\_}jsb{\_}var{\_}real1d -> 1D is incorrect and means scalar) where variables in sb pools are 3D (t{\_}jsb{\_}var{\_}real3d). In result: variables from veg pools need to end with \%ptr (e.g., veg\%pool\%leaf\%carbon\%ptr) where variables from sb pools need to end with \%variable{\_}name(ics:ice,layer,iblk) (note: "layer" can be replace by ":" when all layers should be addressed). Importantly, all variables of sb pools are 3D even though the do not end with {\_}sl (soil layer).\\

\textbf{Operator overload:} is currently available for all veg pools but not for sb pools. An example:
\begin{itemize}
	\item \texttt{veg\%pool = veg\%pool * factor} (is slow but works !)
	\item the same does not work for sb pools, you would have to write:\\
		\texttt{sb\%pool\%microbial\%carbon\%ptr(ics:ice,:,iblk) = \&\\sb\%pool\%microbial\%carbon\%ptr(ics:ice,:,iblk) * factor}\\
		\texttt{sb\%pool\%microbial\%nitrogen\%ptr(ics:ice,:,iblk) = \&\\sb\%pool\%microbial\%nitrogen\%ptr(ics:ice,:,iblk) * factor}\\
		...\\
		\texttt{sb\%pool\%fungi\%carbon\%ptr(ics:ice,:,iblk) = \&\\sb\%pool\%fungi\%carbon\%ptr(ics:ice,:,iblk) * factor}\\
		\texttt{sb\%pool\%fungi\%nitrogen\%ptr(ics:ice,:,iblk) = \&\\sb\%pool\%fungi\%nitrogen\%ptr(ics:ice,:,iblk) * factor}\\
		...
\end{itemize}
~\\
